# Linux TTY and Console: One System or Two?

The relationship between tty and console in Linux kernel has been source of confusion. In this article, we'll break down how tty and console interact in Linux.

The main line is to understand **how user-space writes** and **kernel-space printk** work.

(This website can be helpful to read the source: https://elixir.bootlin.com/linux/)

## Linux 0.01

### overview

The kernel here is straightforward.

The related code is in **kernel/console.c** and **kernel/tty_io.c**

```C
struct tty_struct tty_table[] = {
	{
		{0,
		OPOST|ONLCR,	/* change outgoing NL to CRNL */
		0,
		ICANON | ECHO | ECHOCTL | ECHOKE,
		0,		/* console termio */
		INIT_C_CC},
		0,			/* initial pgrp */
		0,			/* initial stopped */
		con_write,
		{0,0,0,0,""},		/* console read-queue */
		{0,0,0,0,""},		/* console write-queue */
		{0,0,0,0,""}		/* console secondary queue */
	},{
    ...
	},{
    ...
	}
};
```

It's very simple design. Console is seen as one kind of tty.(see **con_write** in the code)

### user space

That means when you write code like:

```C
write(0, "hello, world", 12) // user-space
```

The kernel will check the 0 file descriptor is a console or a rs. If it's a console file descriptor, it will call con_write.

That's how console works in Linux 0.1. It depends on the implementation of tty.

The function call chain is like:

```tex
write -> sys_write ->...->tty_write->con_write or rs_write(serial)
```

The biggest challenge in the implementation of **con_write** is to move the cursor. Not the topic this article will talk about.

### kernel space

Another question: How is **printk** function implemented?

Let's see the code:

```C
int printk(const char *fmt, ...)
{
	va_list args;
	int i;

	va_start(args, fmt);
	i=vsprintf(buf,fmt,args);
	va_end(args);
	__asm__("push %%fs\n\t"
		"push %%ds\n\t"
		"pop %%fs\n\t"
		"pushl %0\n\t"
		"pushl $_buf\n\t"
		"pushl $0\n\t"
		"call _tty_write\n\t" // CHECK HERE!!!
		"addl $8,%%esp\n\t"
		"popl %0\n\t"
		"pop %%fs"
		::"r" (i):"ax","cx","dx");
	return i;
}
```

It calls **tty_write** directly. 

At the point, we can see that **both** user-space writes to tty and kernel-space printk output eventually go through tty_write.

**The system output path is tightly coupled to the tty subsystem.**

```
printk -> **tty_write** -> con_write
write -> sys_write -> ... -> **tty_write** -> con_write or rs_write
```

Linux 0.1 can support at most three**(1 + 2)**  screens and cannot support multiple terminals in one screen.

## Linux 1.0

- Linux 1.0 introduces **PTY**.
- New layer between user input and tty driver: **line discipline**.

### why we need PTY?

PTY provides a mechanism to virtualize a terminal device in user space, allowing programs to act as a terminal controller for other programs that expect a real TTY.

It's master-slave architecture.

Here's a image generated by ChatGPT:

![](https://raw.githubusercontent.com/xiongzile/images/main/20260325131023182.png)

A simple tty application will look like:

```C
#define _XOPEN_SOURCE 600
#include <pty.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

static void die(const char *msg) {
    perror(msg);
    exit(1);
}

int main(void) {
    int master_fd, slave_fd;
    pid_t pid;
    char buf[1024];
    ssize_t n;

    if (openpty(&master_fd, &slave_fd, NULL, NULL, NULL) < 0)
        die("openpty");

    pid = fork();
    if (pid < 0)
        die("fork");

    if (pid == 0) {
        // child: connect slave to stdin/stdout/stderr
        close(master_fd);

        dup2(slave_fd, STDIN_FILENO);
        dup2(slave_fd, STDOUT_FILENO);
        dup2(slave_fd, STDERR_FILENO);

        close(slave_fd);

        execl("/bin/sh", "sh", NULL);
        die("execl");
    }

    // parent: talk to child through master
    close(slave_fd);

    write(master_fd, "echo hello from pty\n", 20);
    write(master_fd, "exit\n", 5);

    while ((n = read(master_fd, buf, sizeof(buf))) > 0) {
        write(STDOUT_FILENO, buf, n);
    }

    close(master_fd);
    waitpid(pid, NULL, 0);
    return 0;
}
```

This is an interesting sample and clarify the relation between master and slave.

The master doesn't read anything from your input, and write two command lines to master_fd directly.

In the case, slave can do nothing but see "hello from pty" and exit.

![](https://raw.githubusercontent.com/xiongzile/images/main/20260325132203343.png)

In real world, here we master need to read(STDOUT_FILENO) first, and write the input to master_fd, which makes the user can **interact with bash**.

Do you understand why the bash executes what you write to master_fd? It's not intuitive.

### what's line discipline?

### user space

You can see in the context, console means display something on screen, not the /dev/console or kernel logs console.

```
write() -> sys_write() -> tty_write() -> line discipline -> vt -> con_write()
```

### kernel space

console_print writes directly to the buffer.

```
printk() -> console_print()
```

when the "/dev/console" is opened, the is_console should be true. But if you see the whole code in Linux 1.0, you'll get that the redirect is only assigned in one case:

```C
case TIOCCONS:
  if (IS_A_PTY_MASTER(dev))
      redirect = other_tty;
  else if (IS_A_PTY_SLAVE(dev))
      redirect = tty;
```

So if you don't use pty the redirect is always NULL, which means "/dev/console" doesn't differ from "/dev/tty".

If you did use pty, and the master process did call **TIOCCONS**, the /dev/console will redirect to the **slave**(other_tty).

We can say the default console is like /dev/tty, no differences.
